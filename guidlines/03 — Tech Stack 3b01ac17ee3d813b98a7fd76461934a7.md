# 03 — Tech Stack

Philosophy: **boring, well-documented, TypeScript end-to-end, minimal moving parts.** Optimized for one developer to build, debug, and operate.

## At a glance

| Layer | Choice | Why |
| --- | --- | --- |
| Language | TypeScript everywhere | One language, shared types/validation, lower mental overhead |
| Frontend | Next.js 15+ (App Router) + React | Server Components reduce boilerplate; huge ecosystem |
| UI kit | Tailwind CSS + shadcn/ui | Fast, consistent, accessible, code you own |
| Backend | Next.js Route Handlers/Server Actions + a clean internal service layer | Avoids running two servers; service layer can later be extracted into a standalone API without rewriting logic |
| ORM | Prisma | Type-safe queries, easy migrations, easy tenant-scoped filters |
| Database | **PostgreSQL, hosted on Supabase** | ACID (mandatory for financial data), JSONB for flexible fields, mature. Supabase gives one dashboard for the DB plus first-class Row-Level Security tooling — and RLS is already central to this product's multi-tenancy model, so this is a genuine architectural fit, not just convenience. It's still plain Postgres underneath — Prisma talks to it directly, no lock-in |
| Auth | **Supabase Auth** (or Clerk for a more polished out-of-the-box invite/org UI) | Don't hand-roll auth. Supabase Auth keeps auth + DB + storage in one vendor/dashboard, which matters for solo-dev operability |
| Jobs/queue | BullMQ + Redis (Upstash Redis is the easy managed pairing) | Reminders, recurring invoices, PDF generation, async DGI submission with retries. Supabase doesn't provide a job queue, so this stays a separate piece |
| PDF generation | @react-pdf/renderer (or Puppeteer) | Devis/factures/BL — react-pdf is simpler to maintain solo |
| File storage | **Supabase Storage** (S3-compatible under the hood) | Attachments, generated PDFs, logos — one less vendor to manage since it lives next to the database and auth in the same project/dashboard |
| Email | Resend or Postmark | Transactional email |
| Payments (phase 2) | CMI gateway | Moroccan card payments, behind a pluggable provider interface |
| Hosting | **Vercel (app) + Supabase (DB, Auth, Storage) + Upstash (Redis)** as the default zero-ops recommendation. VPS Docker Compose (OVH/Scaleway/Hetzner) remains a valid alternative for self-hosting everything. | One dashboard for DB/Auth/Storage instead of three separate vendors. Migrating off Supabase later is a data export, not a rewrite, since it's plain Postgres/Prisma underneath. Keep app code Docker-buildable regardless |
| Monitoring | Sentry + basic uptime check | Minimum viable observability for a solo operator |
| Testing | Vitest (unit) + Playwright (E2E on the critical document flows) | Don't skip tests on Devis→Facture and stock logic |
| CI/CD | GitHub Actions → deploy on merge to main | Simple, free, well documented |

## Why not X

- **Not microservices/NestJS from day one:** a solo dev doesn't need multi-service ops overhead. A modular monolith gets 95% of the maintainability benefit at a fraction of the complexity.
- **Not MongoDB:** ERP data is inherently relational and needs strong consistency (money/stock bugs are real-money bugs). Postgres + JSONB covers flexibility needs.
- **Not a low-code platform / Odoo customization:** the goal is to own custom software, not configure a third-party platform, and to avoid per-user licensing costs.
- **Next.js over separate SPA+API:** fewer moving parts for a solo dev; service-layer discipline keeps a future split possible.

## Environments

- **Local**: Supabase CLI (`supabase start`) spins up a local Postgres + Auth + Storage stack in Docker; Redis via a small Docker Compose service; `next dev` for the app.
- **Staging**: a separate Supabase project, seeded with realistic demo data.
- **Production**: a separate Supabase project (never share staging/prod); pick the Supabase region closest to Morocco (EU-West is the pragmatic default).

## Multi-tenancy at the data layer (summary)

Single database, shared schema, tenant_id on every tenant-owned table, enforced in the Prisma query layer (a wrapped client always injecting tenant_id) AND via Postgres Row-Level Security — implemented directly as **Supabase RLS policies**, keyed off the authenticated user's tenant claim, as defense-in-depth.

**Watch item:** configure Prisma's connection through Supabase's connection pooler (PgBouncer, provided by Supabase) rather than a direct connection, or you'll hit connection limits under serverless/Vercel deployment — get this right during Phase 0, not after launch.
