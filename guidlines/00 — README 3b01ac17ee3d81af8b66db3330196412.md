# 00 — README

> A lightweight, B2B, multi-tenant ERP/CRM for small Moroccan enterprises — "Odoo-small", buildable and maintainable by a single developer.
> 

This is the full specification to hand to a coding agent (Claude Code, Cursor, etc.) so it can build the product with you. Give the agent the whole set, then work module by module — don't ask it to build everything in one shot.

## How to use this with a coding agent

1. **Give the agent all spec pages/files** as project context before writing any code.
2. Ask it to read them in order and summarize its understanding back to you first. Correct anything it gets wrong before it writes code.
3. Build in the order set out in Roadmap (MVP) — Foundation → Core CRM → Sales/Invoicing → Inventory/Purchasing → Compliance (e-invoicing) → Reporting. Do not let the agent jump ahead to modules not yet started.
4. Keep this rule active for the whole project: **one module = one focused session/PR**. Feed the agent the relevant section of Scenarios & Flows and Data Model for the module you're working on, not everything every time.
5. After each module, ask the agent to write/update tests and a short CHANGELOG entry.
6. Treat Tech Stack and Architecture as **binding decisions** — tell the agent explicitly not to introduce new frameworks, ORMs, or infra pieces without flagging it to you first.

## One-line pitch to give the agent

> "We're building Nexa-ERP: a modular, multi-tenant B2B ERP/CRM SaaS for Moroccan small and micro enterprises (1–50 employees). Think 'the 20% of Odoo that 80% of small businesses actually use' — CRM, Sales/Quotes, Invoicing (DGI-compliant e-invoicing), Purchasing, Inventory, and light Accounting — built and maintained by one developer, so simplicity and low operational overhead beat feature completeness every time."
> 

## Non-negotiable ground rules for the agent

- **Simplicity over cleverness.** A solo dev has to debug this at 2am. No microservices, no premature abstractions, no exotic infra.
- **Multi-tenant from day one**, single Postgres database, tenant_id row-level isolation. Retrofitting multi-tenancy later is far more expensive than building it in.
- **Morocco compliance is a first-class citizen**, not a bolt-on: TVA rates, ICE/RC/IF fields, French/Arabic bilingual UI, MAD currency, and the DGI e-invoicing clearance flow must be designed into the data model from the start even if implemented in a later phase.
- **Every module is optional/toggleable per tenant** (mirrors how Odoo apps work) but the underlying schema is shared.
